# 设计：迁移期自建转发（EC2 路由器 mesh + VXLAN over VPC peering）

> 对应代码：`lab/mesh/overlay-mesh.py`（守护进程 v4.2）。测试依据见 [test-report.md](test-report.md)。
> 标注说明：**[文档]** 表示 AWS 官方文档有明确说明；**[实测]** 表示实验环境测出来的结果。

## 1. 目标与非目标

**目标**
1. 迁移期内，让旧容器网络（pod IP 在 VPC CIDR 外）与新 VPC 之间的流量**不经过 TGW**，节省每 GB 的数据处理费。
2. 两端看到的都是真实的 pod IP，不做 SNAT。
3. 单台路由器故障时自动切换，秒级恢复；计划内维护零丢包。
4. 任何时候都可以把入口路由改回 TGW，回退到原来的路径。

**非目标**
- 长期组件：老 VPC 迁空之后就应该下线。
- AZ 级冗余：路由器和 workload 部署在同一个 AZ，同生同死。
- 替代 TGW 的其他职责：IDC 互联、跨 region 等都不在范围内。

## 2. 约束推导

| 约束 | 出处 | 对设计的影响 |
|---|---|---|
| VPC peering 只投递**目的地址在对端 VPC CIDR 内**的包，包进入对端 VPC 后不再查子网路由表 | [实测] | 老 pod 的地址只能出现在内层包里，所以要用隧道封装 |
| 源地址在 VPC 外的包经 peering 也能送达，但这**不是文档承诺的行为** | [实测，同账号] | 设计上不依赖这一点 |
| multi-VPC ENI 不支持跨账号 | [文档] | 不能让一台路由器横跨两个 VPC，所以两侧各放一组 |
| VPC 路由表里同一个目的网段只能有一个下一跳，不支持 ECMP | [文档] | 入口没法按流均衡，只能按网段把不同路由器设为下一跳 |
| 单条流（5 元组）在 cluster placement group 之外上限 5 Gbps；GRE / IPsec 把所有流量合成一条流 | [文档] | 隧道用 VXLAN，按内层流哈希 UDP 源端口，让外层也是多条流 |
| 同 region peering 的 MTU 是 9001；VXLAN 开销 50 字节 | [文档] | 隧道 MTU 设为 8951，并对 TCP 做 MSS clamp |
| 实例带宽规格按方向分别计算 | [文档]、[实测] | 收、发可以同时跑满。单台路由器的约束是「两个方向跨边界流量之和 ≤ 单向规格」 |
| SG 对 TCP/UDP 入、出都是 0.0.0.0/0 全放行时，连接不被跟踪 | [文档] | 路由器 ENI 用全放行的 SG：没有 conntrack 上限，切换后连接状态也不会丢；访问控制交给 NACL |
| 比 local 路由更具体的路由，目的网段必须等于某个子网的 CIDR；VPC 外的网段（pod 段）可以随意写 | [文档] | 老侧 transit 子网的路由表必须包含全部「pod 段 → node ENI」 |
| `ReplaceRoute` 按单个 API 限流：桶容量 50，每秒补 5 个（账号 × region） | [文档]、[实测] | 每侧一次切换要改的路由最多 50 条，否则会被限流。实测 150 条 CIDR 路由要 21 s，换成 prefix list 只要 1 次调用、0.33 s |
| prefix list 可以作为路由的目的地址，按 max entries 计入路由表配额 | [文档]、[实测] | 新侧 pod 段按路由器分组放进 prefix list，每个分组只占一条路由 |

## 3. 方案对比

| 方案 | 切换时间 | 每 GB 费用 | 负载均衡 | 结论 |
|---|---|---|---|---|
| 继续走 TGW | — | TGW 数据处理费 | — | 基线方案，也是降级路径 |
| 老 node 做 SNAT 后走 peering | — | 0 | — | 只能解决「老 → 新」方向；pod IP 丢失；要改容器网络组件。不采用 |
| 把 pod 段加为 secondary CIDR | — | — | — | 加不进去（与现有路由冲突），而且会破坏「pod 段 → ENI」的投递模型。不采用 |
| 路由器主备 + 浮动 ENI（detach / attach） | **28 s** [实测] | ≈ 0 | 无 | 太慢：拔插 ENI 和数据面重编程都在 AWS 侧，脚本优化不了 |
| 路由器主备 + replace-route + VIP（secondary IP 漂移） | 3–5 s [实测] | ≈ 0 | 无 | 可行，但 standby 闲置 |
| **全 active mesh**（本设计） | **隧道段 0.7–1.1 s，入口段 1–2 s** [实测] | ≈ 0（只有 EC2 费用） | 隧道段按流；入口段按网段 | **采用** |
| Gateway Load Balancer 作为入口 | 10–15 s（健康检查最短 5 s × 2） | GWLBE + GWLB 处理费 | 入口按流 | 路由表永远不用改，但每 GB 收费、MTU 降到 8500，还需要设备做 two-arm 转发（未验证）。不想自己维护切换逻辑时可以考虑 |

## 4. 架构

### 4.1 组件

| 组件 | 说明 |
|---|---|
| transit 子网 | 两侧各一个（每个 AZ 一个），只放路由器的数据 ENI |
| 数据 ENI | 每台路由器一块，source/dest check 关闭；打 tag：`overlay-mesh` / `overlay-side` / `overlay-name` / `overlay-index`。**ENI 和实例分开管理**，替换实例时 IP 不变 |
| 路由器 | c8gn 系列，AL2023 arm64；systemd 常驻 `overlay-mesh` 守护进程；所有路由器共用同一份 user_data |
| VXLAN | A 侧每台和 B 侧每台之间各建一条隧道。VNI = 100 + 10 × A 序号 + B 序号；互联地址 169.254.&lt;VNI&gt;.1 / .2（/30）；外层是两台路由器数据 ENI 的 VPC IP；UDP 源端口在 32768–61000 之间按内层流哈希 |
| 入口路由 | 老侧：node 子网路由表里，把新 VPC 网段拆成若干段，每段的 home 是一台 A。新侧：workload 子网和**所有老 pod 会访问的服务所在子网**的路由表里，pod 段按 A/B 分组放进 prefix list，每个 prefix list 一条路由，home 是一台 B |
| EC2 interface endpoint | 路由器在 VPC 内调 Describe* / ReplaceRoute（实测延迟约 45 ms） |
| pod 路由同步 | `podroute_sync.py`：以 node 子网路由表为准，补齐 transit 子网路由表；新出现的 pod 段放进条目最少的 prefix list |
| 降级路径 | TGW 的 attachment、路由，以及 attachment 子网的「pod 段 → node ENI」在迁移期内全部保留 |

### 4.2 数据包路径

**老 pod → 新 VPC 主机**
1. pod → node → node 子网路由表：目的网段对应的 home（例如 A1）的数据 ENI；
2. A1 用多路径路由选出一个 B（按内层五元组哈希），把包封装进 VXLAN，外层 A1 IP → Bx IP，经 peering 送到 Bx；
3. Bx 解封装，内层包从 Bx 的数据 ENI 发出，在新 VPC 内正常投递。源地址仍然是 pod IP。

**新 VPC 主机 → 老 pod**
1. 新侧子网路由表：pod 段所在的 prefix list → home（例如 B2）；
2. B2 用多路径路由选一个 A，封装后发到 Ay；
3. Ay 解封装，内层包从 Ay 的数据 ENI 发出 → transit 子网路由表「pod 段 → node ENI」→ node → pod。

去程和回程通常经过不同的路由器，路径不对称。路由器只做无状态转发，SG 也不跟踪连接，所以这没有问题。

### 4.3 MTU

| 路径 | MTU | 说明 |
|---|---|---|
| 隧道内层 | 8951 | peering 9001 − VXLAN 50；路由器对 TCP SYN 做 MSS clamp |
| 降级到 TGW 之后 | 8500 | TGW 会回 ICMP `Frag needed`，**PMTUD 正常**（实测），前提是 SG / NACL 放行 ICMP |

## 5. 高可用与自治切换规则

### 5.1 健康探测

- **隧道探测**：每 `interval`（0.3 s）向每个隧道对端的互联地址发一个 UDP 3784 探测；超过 `detect`（0.9 s）没有回包，就判定这条隧道不可达。
- **同侧探测**：直接探测同侧其他路由器的数据 ENI IP。
- **回包内容**：对方看到的另一侧可用成员集合（即对我这一侧的「视图」）、对方的配置哈希、对方的健康标志 `ok`、对方可达的隧道对端数量。
- **探测永远应答**：不健康的路由器也照常应答，只是 `ok=false`。
  - 背景：早期版本用「不健康就不应答」实现 fail-closed，结果在两台同时故障时，全网互相都看不见，控制面锁死且无法恢复。
  - 所以要把两件事分开：**可达性**（收得到回包）只用来判断是否隔离；**可用性**（`ok=true`）才决定能否进 ECMP、算不算存活。

### 5.2 自检（fail-closed：不通过就把 ok 设为 false）

满足下面任意一条，就判自己不健康：

- `ip_forward` 不是 1；
- 隧道设备不齐全；
- 依赖（iptables / ethtool）缺失，或者 MSS clamp 规则不在；
- FORWARD 链里有 DROP / REJECT；
- 数据 ENI 的 source/dest check 被打开（通过成员发现读取，最长 10 s 才能发现）；
- 数据网卡不是 up；
- 数据面相关线程（探测应答、对账、入口控制）的心跳超时；
- 存在 drain 文件 `/etc/overlay-mesh.drain`（计划内维护用：自己照常转发，等同伴接管）；
- **被单独隔离**：看得到的隧道对端不到一半，并且同侧同伴看得到的比我多，持续超过 2×detect。恢复时要连续 3 s 不隔离才算健康。

调 EC2 API 的线程（成员发现、路由表查询）卡住，只记 WARN，**不判不健康**：API 慢不应该影响数据面。

### 5.3 数据面

- 隧道网段的路由是多路径的，只包含「可达且 ok」的对端，按内层 L4 哈希（`fib_multipath_hash_policy=1`）。
- **fail-static**：所有对端同时不可用时，保留最后一组下一跳。这种情况更可能是本机过载或网络分区，而不是对端同时故障。
- **blackhole 兜底**：每个隧道网段都有一条 metric 32000 的 blackhole 路由，流量永远不会落到管理网卡的默认路由上。
  - 实测：没有这条兜底时，过载会让流量泄漏到管理网卡。
- 守护进程装的所有路由都打 `proto 199` 标记，每秒对账，删掉不在期望集合里的残留路由。
  - 实测：旧配置留下的一条 /24 blackhole，曾经在成员变化时吞掉全部 pod 流量。

### 5.4 入口决策

- **判定同侧 X 故障**：X 的直接探测超时（或者回包 `ok=false`），**并且**隧道对端的新鲜视图里，有多数派明确说 X 不可用。证据不足时一律当作存活：宁可不切，也不误切。
- **ISOLATED**：看得到的隧道对端不足一半时，不做任何入口决策。
- **接管**：home 故障后，存活的同侧路由器用 rendezvous hash 选出接管者，只改「下一跳 = 故障路由器 ENI」的那几条路由。
- **收回**：home 自己健康满 `hold`（10 s），**并且**被多数隧道对端持续看到满 `hold`，才收回自己的路由。
- **防抖**：每条路由 10 s 内最多切换一次；60 s 内切换 3 次以后，退避到 60 s。
- **只碰本侧路由器的路由**：路由当前指向 TGW、其他目标或者已经被删掉，一律视为人工操作，不改。
- **冻结**：路由表打了 `overlay-freeze=true` 标签，整张表都不动（人工降级时使用）。
- **配置不一致**：同侧有路由器的配置哈希和我不同时，只做接管、不做收回，避免两个 home 互抢。

### 5.5 成员发现

- 启动时，通过 IMDS 拿到本机 instance-id，再找挂在本机上、带 tag 的数据 ENI，从而确定自己的身份。
- 每 10 s 用 `DescribeNetworkInterfaces` 查一次带同一个 mesh tag、并且已挂载的 ENI，作为成员列表。
- **防抖**：连续 3 次查询都不在，才移除这个成员；如果查询结果里对侧成员变成 0，就忽略这次结果。
- **跨账号**：本账号看不到对侧的 ENI，对侧成员由配置里的 `static_peers` 提供，本侧继续自动发现。

### 5.6 降级

整体降级（L3）有两种做法：
- 运行 `fallback_tgw.py down`：先冻结入口路由表，等 3 s，再把所有入口路由并发改到 TGW；
- 或者手工打冻结标签后，用 replace-route 逐条改。

恢复时执行 `restore`。实测降级和恢复都是 1–2 s，0 丢包。

### 5.7 参数（定稿）

| 参数 | 值 | 说明 |
|---|---|---|
| interval | 0.3 s | 探测间隔 |
| detect | 0.9 s | 判定超时（3 个间隔） |
| hold | 10 s | 收回前要求的稳定时间 |
| discover | 10 s | 成员发现周期 |
| miss_limit | 3 | 成员移除前要求的连续缺失次数 |
| min_move | 10 s | 单条路由的最小切换间隔 |

更激进的参数（0.1 s / 0.5 s）切换更快（隧道段约 0.45 s，入口段约 1.1 s），但过载时更容易误判。

## 6. 容量与费用

### 6.1 单台转发能力

实测条件：c8gn.16xlarge，内核转发 + VXLAN，单块数据 ENI（16 个队列）。

| 维度 | 实测 | 规划值（70%） |
|---|---|---|
| 带宽（两个方向之和） | 199 Gbps（实例规格上限） | 140 Gbps |
| PPS（两个方向之和） | ≥ 6 Mpps 无丢包（再往上，测试发生器先到上限） | 4.2 Mpps |

- 哪个维度先到上限取决于平均包长：平均 4 KB 时，两个维度差不多同时到；平均 1 KB 时只有约 34 Gbps，PPS 先到。
- **平均包长**：用 CloudWatch 的 EC2 指标估算，`NetworkIn` / `NetworkPacketsIn`（出方向同理），按 workload 汇总后取峰值；如果有 VPC flow logs，也可以用 bytes / packets 字段算。
- **每侧台数** = ⌈ 跨边界峰值 ÷ 单台规划值 ⌉ + 1。
- 提升 PPS 的选项（未测）：拆成两块数据 ENI（32 个队列）、换 c8gn.24xlarge、用 XDP / VPP。

### 6.2 费用对比（示例：法兰克福按需价，2026-11）

| 方案 | 计费方式 |
|---|---|
| TGW | 每 GB 数据处理费 + attachment 小时费 |
| 本方案 | 只有 EC2 费用。c8gn.16xlarge 约 $4.32/h，每侧 2 台共 4 台约 $415/天；同 AZ 的 peering 流量免费 |
| GWLB | GWLBE $0.0035/GB + GWLB $0.0042/GLCU，合计约 $0.0077/GB，另有小时费 |

**盈亏平衡点**：按 TGW $0.02/GB 计，4 台 c8gn.16xlarge 约等于每天 21 TB 跨边界流量。如果跨边界流量持续明显高于这个值、迁移周期又长于 2 个月，才值得引入本方案；否则直接走 TGW 更简单。

## 7. 运维接口

| 操作 | 方式 |
|---|---|
| 计划内维护 | 在路由器上建 `/etc/overlay-mesh.drain` 文件；删除这个文件即恢复 |
| 人工接管路由表 | 给路由表打 `overlay-freeze=true` 标签 |
| 修改配置 / 升级 | 修改 `/etc/overlay-mesh.json` 后重启服务；新实例由 user_data 安装 |
| 关键日志 | `/var/log/overlay-mesh.log`：`MEMBERS` / `SELF` / `TUN` / `SIDE` / `TAKE` / `ISOLATED` / `FAILSTATIC` / `CONFIG-MISMATCH` / `FREEZE` / `STALE` / `MEMBER-GONE` / `WARN` / `ERR` |

## 8. 已知限制

1. 入口段的故障切换依赖 EC2 API。API 不可用时，入口在故障路由器上的那部分流量要等 API 恢复。
2. 入口按网段分配，不是按流，负载均衡粒度受网段大小影响。
3. 只断隧道、同侧互探正常时，检测要走「隔离 → 判自己不健康 → 同伴判死」这条链，约 3.5 s。
4. source/dest check 被误开时，最长 10 s 才能检测到（取决于成员发现周期）。
5. 每侧最多 9 台路由器（受 VNI 编号方案限制）。
6. 过载时本机会丢包。守护进程只能保证不误切、不漏到默认路由，扛不住过载，所以容量规划要留 30% 余量。
7. 不做 AZ 级冗余。
