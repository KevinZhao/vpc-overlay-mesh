# 测试报告

> 守护进程定稿版本 v4.2；测试脚本在 `lab/mesh/`、`lab/scripts/` 下，复现方法见 [lab-runbook.md](lab-runbook.md)。
> 所有数字都来自实验环境，**生产上线前必须按 §6 重新验证**。

## 1. 测试环境

| 项 | 配置 |
|---|---|
| 拓扑 | 同一个账号、同一个 AZ 内的两个 VPC + VPC peering。老 VPC 里的「old-node」用 netns 模拟 VPC CIDR 外的 pod（100.64.10.10 / .70 / .140 / .200），VPC 路由表写「pod 段 → node ENI」；新 VPC 里的「new-host」带 4 个地址 |
| 路由器 | 每侧 3 台 c8gn.large（吞吐测试临时升到 c8gn.16xlarge），AL2023 arm64 |
| 入口 | 老侧把新 VPC 网段拆成 4 个 /26，分给 A1–A3；新侧用 3 个 prefix list，每个装 90 多个 pod 段，分给 B1–B3 |
| 参数 | interval 0.3 s / detect 0.9 s / hold 10 s（生产参数） |
| 测试流量 | `flowprobe.py`：4 个 pod 源 × 4 个目的 × 2 个端口 = 32 条 UDP 流，每条每 10 ms 一个包，统计每条流 ≥ 50 ms 的中断。`httpprobe.py`：32 条 HTTP 连接，客户端超时 1 s |
| 故障注入 | 在约定的时间点用 SSM 执行，例如 iptables、sysctl、systemd、sysrq，或调 EC2 API；全部可逆，脚本结束时自动恢复 |

## 3. 结果

### 3.1 基础

| 项 | 结果 |
|---|---|
| 双向连通 | pod ↔ 新 VPC 主机双向都通，对端抓包看到的源地址是 pod IP |
| MTU | 带 DF 的 8951 字节内层包能通，8952 字节被拒（frag needed）；TCP 通过 MSS clamp 正常 |
| peering 对 VPC 外地址的处理（同账号） | 去程 `src = pod IP` 经 peering **能送达**；回程 `dst = pod IP` 经 peering **被丢弃**。前者不是文档承诺的行为，设计上不依赖它 |

### 3.2 切换原语对比（用来决定 HA 机制）

| 原语 | 结果 |
|---|---|
| 浮动 ENI（`detach --force` + `attach`） | 中断 **28 s**：detach 之后数据面还在旧实例上跑约 9 s，变为 available 用 6.5 s，attach 用 5.5 s，系统识别网卡用 4.4 s，之后数据面还要 11.6 s 才收敛；TCP 长连接能存活 |
| `ReplaceRoute` | API 1.4–2.3 s（从实验环境外部调用）/ 0.25–0.37 s（VPC 内调用）；API 返回后 0.3–0.4 s 生效 |
| secondary IP 漂移 | 约 2.5 s 稳定 |
| 主备 + replace-route + VIP | 端到端 2.7–4.6 s；改 1 张路由表和改 21 张一样快 |
| 路由规模：150 条 CIDR 路由并发替换 | **21.2 s**：前 50 条 1.6 s 完成，之后按每秒 5 条补充，被限流 139 次 |
| prefix list（一个 PL 装 92 个 pod 段） | **1 次 API，0.33 s** |

### 3.4 特殊场景

| 场景 | 结果 | 说明 |
|---|---|---|
| 数据 ENI 的 source/dest check 被打开 | +10.4 s 检测到，+11.0 s 被接管；36 s 内没有丢包 | 检测依赖成员发现周期，最长 10 s。打开之后转发没有马上中断，**不能据此推断误开没有影响** |
| 对侧全部 ENI 的 tag 被删 | 0 影响 | 发现结果里对侧成员为 0 时，忽略本次结果 |
| 只删一台的 tag | 约 22 s 后中断 3.5–3.65 s | 防抖期（30 s）过后它被移出成员，它自己隔离下线，同伴接管。属于配置误操作，不要用删 tag 的方式下线路由器 |
| 内核崩溃（sysrq） | 1.35–1.44 s | **崩溃 40 s 后 EC2 状态检查仍然是 ok**，不能靠它发现路由器故障 |
| 强制停机（`stop --force`） | 0 丢包，+4.1 s 检测到 | OS 仍然先停了服务，效果等于一次 drain |
| 摘掉一台的 ENI，每侧只剩 2 台；再让另一台硬故障 | 摘除时入口中断约 2 s；之后的故障中断 1.68 s | N=2 时切换正常 |
| 只给一台推一份 home 不同的配置 | 0 影响 | 报 `CONFIG-MISMATCH`，只接管不收回 |
| 时钟跳 +120 s | 0 影响，没有任何事件 | 计时全部用 monotonic |
| 入口路由被人工改到 TGW（没打冻结标签） | 25 s 后仍然指向 TGW | 不碰非路由器目标 |
| 入口路由被删 | 30 s 内重试 0 次 | 没有重试风暴 |
| 强制轮转日志 | 守护进程照常写新文件 | copytruncate 有效 |

| 项 | 结果 |

### 3.7 EC2 API 不可用

在同侧两台路由器上封掉到 EC2 endpoint 的 443，然后让第三台硬故障，10 s 后恢复 API。

| 项 | 结果 |
|---|---|
| 隧道段 | 0.6–1.1 s，不依赖 API |
| 入口段 | 11.15 s（≈ API 不可用时长 + 约 1 s） |

### 3.8 pod 路由同步

| 项 | 结果 |
|---|---|
| 新 node 上线（容器网络控制器只写了 node 子网路由表） | 同步前，新 VPC 访问新 pod **不通**；同步后 4.5–9.2 s 连通 |
| 幂等 | 再跑一次没有动作 |
| node 下线 | transit 路由和 prefix list 条目都被删干净 |
| 护栏：权威路由表为空 | 中止，不做任何修改 |
| 护栏：一次要删 6 条，超过上限 5 | 中止；加大上限后才执行 |
| 护栏：prefix list 已满 | 中止，并给出待处理的段 |

### 3.9 滚动替换

drain → `terraform apply -replace` 替换实例（数据 ENI 和 IP 不变）→ 新实例从 user_data 自动安装并加入 → 健康满 HOLD 后收回：**360 s 全程 32 条流 0 丢包**。每台约 5 分钟，其中拆卸 ENI 约 3.5 分钟。

### 3.10 跨账号模拟

两侧 ENI 打不同的 mesh tag，让每侧只能发现本侧成员，对侧成员只来自 `static_peers`：mesh 正常建立；A 侧硬故障中断 1.32 s，B 侧 2.17 s；恢复后自动收回。

### 3.11 吞吐与 PPS（单对路由器，c8gn.16xlarge，内核转发 + VXLAN）

| 负载 | 结果 |
|---|---|
| TCP 单向 64 流 | **199.4 Gbps**；瓶颈是实例带宽规格，softirq 只用了 11 / 64 核 |
| TCP 双向 64 流 | 96.8 + 102.5 = 199.3 Gbps |
| UDP 1400 B，固定速率 | 6 Mpps（67 Gbps），丢包 0.0009% |
| UDP 512 B / 64 B，固定速率 | 路由器完整转发了 6 Mpps / 4.5 Mpps；更高速率下，丢包发生在测试接收端的 socket 缓冲区 |

## 4. 测试中发现并修复的问题

| # | 现象 | 根因 | 修复 |
|---|---|---|---|
| 1 | 隧道上的路由不通 | 路由没有下一跳，内核对最终目的地址发 ARP | 隧道配 /30 互联地址，路由写成 `via <对端> onlink` |
| 2 | 热插拔 ENI 之后，回内网的路由写入失败 | 网卡的直连路由比脚本晚出现 | 所有路由都加 `onlink`，并每秒对账 |
| 3 | 过载时流量泄漏到管理网卡 | 探测包丢失 → 隧道路由被删除 → 流量落到默认路由 | fail-static + blackhole 兜底 |
| 4 | 新路由器缺依赖（iptables），MSS clamp 没有生效 | 开机时 dnf 因为 rpm 锁冲突失败 | user_data 加重试和校验；自检要求依赖和 MSS 规则都在 |
| 5 | 过载的路由器把健康的同伴判死、抢它们的流量 | 判死规则是「没人说它活着」 | 改为「多数派明确说它不可用」+ ISOLATED |
| 6 | 改配置后，一次成员变化导致全部 pod 流量被黑洞 | 旧配置留下的 /24 blackhole 比新路由更具体 | 自管路由打 proto 标记，每秒清理残留 |
| 7 | API 超时卡住了入口控制循环；同一条路由被改了两次 | 同步调用；防重入窗口比调用耗时短 | 查询放到后台线程；防重入改为按调用完成判断；不在 SDK 内重试 |
| 8 | pod 路由同步误删 prefix list 里的条目；连续修改报 `VersionMismatch` | 把不认识的条目当成已下线的 pod 段；prefix list 修改是异步的 | 只管理自己加入的条目；每个 PL 一次调用，并等 `modify-complete` |
| 9 | 纯网络故障恢复后，不经过 HOLD 就收回；单向可达时无限互抢 | HOLD 只和自检状态挂钩 | 收回还要求被对端持续看到满 HOLD；单条路由切换有退避 |
| 10 | 路由被人工改到 TGW 后又被抢回；路由被删后无限重试 | 不区分目标类型 | 只处理指向本侧路由器 ENI 的路由 |
| 11 | 一次查询结果为空，就拆光全部隧道 | 成员变动没有防抖 | 连续 3 次缺失才移除；对侧成员为 0 时忽略 |
| 12 | **两台同时故障时，全网控制面锁死，无法恢复** | 「不健康就不应答探测」：对侧大面积故障 → 本侧全部隔离 → 全部停止应答 → 谁都看不见谁 | 探测永远应答，回包里带 `ok` 标志；隔离判定要和同侧对比 |
| 13 | 滚动升级时，新版本解析旧版本回包报错 | 回包格式变了 | 回包格式向后兼容 |
| 14 | EC2 API 变慢时，路由器把自己判成不健康 | API 线程的心跳被算进了健康判定 | API 线程卡住只告警 |
| 15 | sdc / FORWARD DROP / 网卡 down 时检测不到故障 | 自检只看 ip_forward | 自检覆盖转发面 |

## 6. 上线前必须在生产环境验证的事项

| # | 场景 | 为什么实验环境测不了 | 验证方法 | 严重度 |
|---|---|---|---|---|
| C1 | 老 pod 访问新侧**托管服务**（NLB、RDS、ElastiCache、MSK、interface endpoint、EKS 控制面 ENI 等） | 实验环境只有 EC2 主机。这些服务所在子网的路由表如果没有「pod 段 → B 路由器」，回包会走别的路径或被黑洞 | 列出老 pod 访问的所有新侧服务及其子网，全部挂上 prefix list 路由；每类服务各做一次双向探测 | 高 |
| C2 | 新侧 CNI 对「目的地址在 VPC 外」的 SNAT | 例如 AWS VPC CNI 默认会对 VPC 外的目的地址做 SNAT（`AWS_VPC_K8S_CNI_EXTERNALSNAT=false`），老 pod 看到的就是 node IP | 在新侧 pod 上抓包确认；必要时配置 `EXCLUDE_SNAT_CIDRS` | 高 |
| C3 | 旧容器网络的**路由控制器**对 node 子网路由表的处理 | 实验环境里没有这个控制器。它可能会清理自己不认识的路由，也会和我们争路由表配额 | 确认控制器的对账逻辑；灰度时先在一张表上观察 24 h | 高 |
| C4 | 真实跨账号（IAM、assume role、peering 语义） | 实验环境是同账号，只模拟了「对侧不可见」 | 在两个账号上部署一对一的最小环境，复测 3.1 和 3.3 | 高 |
| C5 | 老侧路由表的数量和条目配额 | 取决于实际的路由表结构 | 每次切换要改的路由数 = 路由表数 × 段数，需要 ≤ 50 | 中 |
| C6 | NACL 和有状态设备 | 实验环境没有 NACL，也没有防火墙 | NACL 必须放行 UDP 4789 / 3784 / 3785 和 ICMP frag-needed；复测 MTU 和降级 | 中 |
| C7 | 真实流量模式（包长分布、几十万条并发流、elephant flow） | 实验环境用的是合成流量 | 用 CloudWatch 估算包长和峰值；用生产规格做一次 IMIX + 大并发测试 | 中 |
| C8 | 生产规格满载下的切换时延 | 切换测试都在 c8gn.large 上做 | 生产规格上线前，在满载下做一次 drain 和一次硬故障演练 | 中 |
| C9 | 按 pod IP 写的 SG 和审计规则 | — | 确认新侧 SG 覆盖了老 pod 地址池 | 低 |
| C10 | 跨 AZ 的残留实例 | 路由器只部署在一个 AZ | 迁移前对齐 AZ，或者接受跨 AZ 的费用和单点风险 | 低 |

## 7. 结论的适用范围

1. 切换时延是在 c8gn.large、每侧 3 台、32 条合成流、单张入口路由表、同账号、没有 NACL 的条件下测的。生产环境要重新测。
2. 吞吐和 PPS 是在单对路由器、64 条流、用 node IP 收发的条件下测的；PPS 的真实上限被测试发生器和接收端限制住了，没有测到。
3. 「PMTUD 正常」的前提是路径上放行 ICMP。
